## Overview

This project uses Alembic for database schema migrations with PostgreSQL. All migrations are stored in `backend/migrations/versions/` and are version-controlled.

**Key Principles:**
- Always test migrations in a development environment first
- Never skip migrations or modify the migration history
- Always create both upgrade() and downgrade() functions
- Use meaningful revision IDs and descriptions
- Back up production database before applying migrations

**Database Models:**
- User, Recipe, Ingredient, MealPlan, GroceryCart, CartItem
- IngredientCategory, Allergen, IngredientAllergen, SubstitutionRule
- MealPlanRecipe (join table)

## Creating New Migrations

### When to Create Migrations

**Create a migration when:**
- Adding/removing tables
- Adding/removing columns
- Changing column types or constraints
- Adding/removing indexes
- Modifying foreign keys
- Adding/removing unique constraints

**Use raw SQL when:**
- Performing data migrations (updating existing rows)
- Complex multi-step operations requiring data preservation
- Operations not well-supported by Alembic

### Naming Conventions

Use descriptive names with timestamp prefix:

```bash
# Format: NNN_description_of_change
# Examples:
006_add_user_preferences_table
007_add_email_index_to_users
008_rename_meal_plan_status_column
009_add_dietary_restrictions_to_recipes
```

### Autogenerate vs Manual Scripts

#### Autogenerate (Recommended for Schema Changes)

Best for adding/removing tables and columns:

```bash
# Navigate to backend directory
cd backend

# Create autogenerated migration
alembic revision --autogenerate -m "add user_preferences table"

# This will:
# 1. Compare current database schema to SQLAlchemy models
# 2. Generate upgrade() and downgrade() functions
# 3. Create a new file in migrations/versions/
```

**Example autogenerated migration:**

```python
"""Add user_preferences table.

Revision ID: 006_add_user_preferences
Revises: 005_add_dietary_tags
Create Date: 2025-12-05

"""
from alembic import op
import sqlalchemy as sa

# revision identifiers, used by Alembic.
revision = '006_add_user_preferences'
down_revision = '005_add_dietary_tags'
branch_labels = None
depends_on = None


def upgrade():
    """Add user_preferences table."""
    op.create_table(
        'user_preferences',
        sa.Column('id', sa.Integer(), nullable=False),
        sa.Column('user_id', sa.Integer(), nullable=False),
        sa.Column('dietary_restrictions', sa.JSON(), nullable=True),
        sa.Column('favorite_cuisines', sa.JSON(), nullable=True),
        sa.Column('created_at', sa.DateTime(), nullable=False),
        sa.Column('updated_at', sa.DateTime(), nullable=False),
        sa.ForeignKeyConstraint(['user_id'], ['users.id'], ondelete='CASCADE'),
        sa.PrimaryKeyConstraint('id')
    )
    op.create_index('ix_user_preferences_user_id', 'user_preferences', ['user_id'])


def downgrade():
    """Remove user_preferences table."""
    op.drop_index('ix_user_preferences_user_id', table_name='user_preferences')
    op.drop_table('user_preferences')
```

#### Manual Scripts (Required for Data Migrations)

Best for data transformations and complex operations:

```bash
# Create empty migration
alembic revision -m "migrate recipe difficulty values"

# Edit the generated file manually
```

**Example manual data migration:**

```python
"""Migrate recipe difficulty values from numeric to text.

Revision ID: 007_migrate_difficulty_values
Revises: 006_add_user_preferences
Create Date: 2025-12-05

"""
from alembic import op
import sqlalchemy as sa

revision = '007_migrate_difficulty_values'
down_revision = '006_add_user_preferences'
branch_labels = None
depends_on = None


def upgrade():
    """Convert numeric difficulty (1-5) to text (easy/medium/hard)."""
    # Add new column
    op.add_column('recipes', sa.Column('difficulty_text', sa.String(20), nullable=True))

    # Migrate data
    connection = op.get_bind()
    connection.execute(sa.text("""
        UPDATE recipes
        SET difficulty_text = CASE
            WHEN difficulty_numeric <= 2 THEN 'easy'
            WHEN difficulty_numeric <= 4 THEN 'medium'
            ELSE 'hard'
        END
    """))

    # Make column non-nullable after data migration
    op.alter_column('recipes', 'difficulty_text', nullable=False)

    # Drop old column
    op.drop_column('recipes', 'difficulty_numeric')


def downgrade():
    """Revert text difficulty back to numeric."""
    # Add old column back
    op.add_column('recipes', sa.Column('difficulty_numeric', sa.Integer(), nullable=True))

    # Migrate data back
    connection = op.get_bind()
    connection.execute(sa.text("""
        UPDATE recipes
        SET difficulty_numeric = CASE
            WHEN difficulty_text = 'easy' THEN 2
            WHEN difficulty_text = 'medium' THEN 3
            WHEN difficulty_text = 'hard' THEN 5
        END
    """))

    # Make column non-nullable
    op.alter_column('recipes', 'difficulty_numeric', nullable=False)

    # Drop new column
    op.drop_column('recipes', 'difficulty_text')
```

### Common Migration Patterns

#### Adding a Column with Default Value

```python
def upgrade():
    """Add is_active column with default value."""
    op.add_column('users',
        sa.Column('is_active', sa.Boolean(),
                  nullable=False, server_default='true'))
```

#### Adding an Index

```python
def upgrade():
    """Add index on email column for faster lookups."""
    op.create_index('ix_users_email', 'users', ['email'], unique=True)

def downgrade():
    """Remove email index."""
    op.drop_index('ix_users_email', table_name='users')
```

#### Renaming a Column

```python
def upgrade():
    """Rename column for clarity."""
    op.alter_column('recipes', 'desc', new_column_name='description')

def downgrade():
    """Revert column name."""
    op.alter_column('recipes', 'description', new_column_name='desc')
```

## Testing Migrations Locally

### Option 1: Docker Compose (Recommended)

Test migrations in an isolated PostgreSQL container:

```bash
# Start PostgreSQL container
cd infrastructure
docker-compose up -d postgres

# Wait for PostgreSQL to be ready
sleep 5

# Set environment variables
export DATABASE_URL="postgresql://postgres:postgres@localhost:5432/recipe_app"

# Run migrations
cd ../backend
alembic upgrade head

# Verify schema
psql $DATABASE_URL -c "\dt"  # List tables
psql $DATABASE_URL -c "\d recipes"  # Describe recipes table

# Test rollback
alembic downgrade -1
alembic upgrade head

# Clean up
docker-compose down -v  # Remove container and volumes
```

### Option 2: Local PostgreSQL

Test against your local PostgreSQL installation:

```bash
# Create test database
createdb recipe_app_test

# Set environment variables
export DB_NAME="recipe_app_test"
export DB_USER="postgres"
export DB_PASSWORD="postgres"
export DB_HOST="localhost"
export DB_PORT="5432"

# Run migrations
cd backend
alembic upgrade head

# Verify
psql -U postgres -d recipe_app_test -c "\dt"

# Clean up
dropdb recipe_app_test
```

### Option 3: Test Database with pytest

Use the test suite infrastructure:

```bash
# Set test database
export TEST_DB_NAME="recipe_app_test"

# Run migration tests
cd backend
pytest tests/integration/test_db_backup_restore.py -v

# Or run all integration tests
pytest tests/integration/ -v
```

### Verifying Migrations

After applying migrations, verify:

1. **Schema structure:**
```bash
# List all tables
psql $DATABASE_URL -c "\dt"

# Describe specific table
psql $DATABASE_URL -c "\d+ recipes"

# Check indexes
psql $DATABASE_URL -c "\di"

# Check constraints
psql $DATABASE_URL -c """
SELECT conname, contype, conrelid::regclass
FROM pg_constraint
WHERE conrelid = 'recipes'::regclass;
"""
```

2. **Foreign key relationships:**
```bash
psql $DATABASE_URL -c """
SELECT
    tc.table_name,
    kcu.column_name,
    ccu.table_name AS foreign_table_name,
    ccu.column_name AS foreign_column_name
FROM information_schema.table_constraints AS tc
JOIN information_schema.key_column_usage AS kcu
  ON tc.constraint_name = kcu.constraint_name
JOIN information_schema.constraint_column_usage AS ccu
  ON ccu.constraint_name = tc.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY';
"""
```

3. **Migration history:**
```bash
# Check current revision
alembic current

# Show migration history
alembic history

# Show detailed history
alembic history --verbose
```

## Deploying to Environments

### Development Environment

Simplest deployment - apply migrations immediately:

```bash
# SSH to development server or use Railway CLI
railway run alembic upgrade head

# Or with environment variables
DATABASE_URL="postgresql://..." alembic upgrade head
```

### Staging Environment

Include pre-flight checks and validation:

```bash
#!/bin/bash
# deploy_staging_migrations.sh

set -euo pipefail

echo "=== Pre-flight Checks ==="

# 1. Check current migration status
echo "Current migration status:"
alembic current

# 2. Show pending migrations
echo "Pending migrations:"
alembic upgrade head --sql | head -50

# 3. Confirm with operator
read -p "Apply these migrations to staging? (yes/no): " confirm
if [ "$confirm" != "yes" ]; then
    echo "Aborted"
    exit 1
fi

echo "=== Applying Migrations ==="

# 4. Apply migrations
alembic upgrade head

# 5. Verify migration status
echo "New migration status:"
alembic current

# 6. Run smoke tests
echo "Running smoke tests..."
pytest tests/integration/test_grocery_cart_api.py -v

echo "=== Migration Complete ==="
```

### Production Environment

Most rigorous process with backup, monitoring, and rollback capability:

```bash
#!/bin/bash
# deploy_production_migrations.sh

set -euo pipefail

BACKUP_DIR="/tmp/db_backups"
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="${BACKUP_DIR}/pre_migration_${TIMESTAMP}.sql.gz"

echo "=== Production Migration Deployment ==="
echo "Timestamp: $TIMESTAMP"

# 1. Create backup before migration
echo "Step 1: Creating database backup..."
./infrastructure/scripts/backup_database.sh "pre_migration_${TIMESTAMP}"

# 2. Verify backup integrity
echo "Step 2: Verifying backup integrity..."
gzip -t "$BACKUP_FILE"
echo "Backup verified: $BACKUP_FILE"

# 3. Check current migration status
echo "Step 3: Current migration status:"
alembic current

# 4. Preview migration SQL
echo "Step 4: Migration SQL preview:"
alembic upgrade head --sql | head -100

# 5. Confirm with DBA
read -p "Apply migrations to PRODUCTION? Type 'APPLY' to confirm: " confirm
if [ "$confirm" != "APPLY" ]; then
    echo "Aborted - confirmation not received"
    exit 1
fi

# 6. Enable maintenance mode (if applicable)
echo "Step 6: Enable maintenance mode..."
# curl -X POST https://api.yourapp.com/admin/maintenance/enable

# 7. Apply migrations with timeout
echo "Step 7: Applying migrations..."
timeout 300 alembic upgrade head || {
    echo "ERROR: Migration timed out!"
    exit 1
}

# 8. Verify schema
echo "Step 8: Verifying schema..."
alembic current

# 9. Run critical smoke tests
echo "Step 9: Running smoke tests..."
pytest tests/integration/test_grocery_cart_api.py::test_create_cart -v

# 10. Monitor application health
echo "Step 10: Monitoring application health..."
sleep 10
curl -f https://api.yourapp.com/health || {
    echo "ERROR: Health check failed!"
    echo "Rolling back migration..."
    alembic downgrade -1
    exit 1
}

# 11. Disable maintenance mode
echo "Step 11: Disable maintenance mode..."
# curl -X POST https://api.yourapp.com/admin/maintenance/disable

echo "=== Migration Complete ==="
echo "Backup location: $BACKUP_FILE"
echo "Keep this backup for 7 days minimum"
```

### Zero-Downtime Migrations

For large tables or high-traffic applications:

#### Adding a Column (Safe)

```python
def upgrade():
    """Add column - safe for zero downtime."""
    # Step 1: Add column as nullable
    op.add_column('recipes', sa.Column('new_field', sa.String(100), nullable=True))

    # Step 2: Backfill data in batches (optional)
    # Do this in a separate maintenance window or background job

    # Step 3: Make non-nullable in future migration after backfill
```

#### Adding an Index (Safe with CONCURRENTLY)

```python
def upgrade():
    """Add index without blocking writes."""
    # Use raw SQL for CONCURRENTLY (not supported in Alembic directly)
    connection = op.get_bind()
    connection.execute(sa.text(
        'CREATE INDEX CONCURRENTLY ix_recipes_title ON recipes (title)'
    ))

def downgrade():
    """Drop index."""
    op.drop_index('ix_recipes_title', table_name='recipes')
```

**Note:** CONCURRENTLY cannot run in a transaction, so use:
```python
from alembic import op

def upgrade():
    """Add index concurrently."""
    # Disable transaction for this migration
    connection = op.get_bind()
    connection.execution_options(isolation_level="AUTOCOMMIT")
    connection.execute(sa.text(
        'CREATE INDEX CONCURRENTLY ix_recipes_title ON recipes (title)'
    ))
```

## Rolling Back Migrations

### Single Version Rollback

Undo the last migration:

```bash
# Rollback one version
alembic downgrade -1

# Verify
alembic current
```

### Multiple Version Rollback

Rollback to a specific revision:

```bash
# Show migration history
alembic history

# Rollback to specific revision
alembic downgrade 005_add_dietary_tags

# Or rollback multiple steps
alembic downgrade -3  # Go back 3 migrations
```

### Emergency Rollback Procedure

When production is broken and you need to rollback immediately:

```bash
#!/bin/bash
# emergency_rollback.sh

set -euo pipefail

echo "=== EMERGENCY ROLLBACK ==="

# 1. Identify problematic migration
echo "Current migration:"
alembic current

# 2. Enable maintenance mode
echo "Enabling maintenance mode..."
# curl -X POST https://api.yourapp.com/admin/maintenance/enable

# 3. Rollback one version
echo "Rolling back migration..."
alembic downgrade -1

# 4. Verify rollback
echo "New migration status:"
alembic current

# 5. Test application
echo "Testing application..."
curl -f https://api.yourapp.com/health

# 6. Disable maintenance mode
echo "Disabling maintenance mode..."
# curl -X POST https://api.yourapp.com/admin/maintenance/disable

echo "=== ROLLBACK COMPLETE ==="
echo "Investigate the failed migration before retrying"
```

### Post-Rollback Data Consistency Checks

After rolling back, verify data integrity:

```sql
-- Check for orphaned records (foreign keys)
SELECT COUNT(*) FROM cart_items ci
WHERE NOT EXISTS (
    SELECT 1 FROM grocery_carts gc WHERE gc.id = ci.cart_id
);

-- Check for NULL values that shouldn't exist
SELECT COUNT(*) FROM recipes WHERE title IS NULL;

-- Check constraint violations
SELECT * FROM recipes WHERE prep_time < 0;

-- Verify row counts match expectations
SELECT
    'users' as table_name, COUNT(*) as row_count FROM users
UNION ALL
SELECT 'recipes', COUNT(*) FROM recipes
UNION ALL
SELECT 'ingredients', COUNT(*) FROM ingredients;
```

## Troubleshooting

### Check Migration Status

```bash
# Current migration
alembic current

# Show full history
alembic history --verbose

# Check if database is ahead of code
alembic current
# Compare to: ls -1 backend/migrations/versions/
```

### Stuck Migrations

**Symptom:** Migration hangs or times out

**Causes:**
- Lock contention on large tables
- Long-running queries blocking migration
- Insufficient resources

**Solutions:**

1. **Check for blocking queries:**
```sql
-- Find blocking queries
SELECT
    pid,
    usename,
    pg_blocking_pids(pid) as blocked_by,
    query as blocked_query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- Kill blocking query (use with caution!)
SELECT pg_terminate_backend(pid);
```

2. **Check table locks:**
```sql
SELECT
    t.relname,
    l.locktype,
    l.mode,
    l.granted
FROM pg_locks l
JOIN pg_class t ON l.relation = t.oid
WHERE t.relname = 'recipes';
```

3. **Break up large migrations:**
```python
# Instead of single large migration, use batches
def upgrade():
    """Update large table in batches."""
    connection = op.get_bind()

    # Process in batches of 1000
    batch_size = 1000
    offset = 0

    while True:
        result = connection.execute(sa.text(f"""
            UPDATE recipes
            SET processed = true
            WHERE id IN (
                SELECT id FROM recipes
                WHERE processed IS NULL
                LIMIT {batch_size}
            )
        """))

        if result.rowcount == 0:
            break

        offset += batch_size
        print(f"Processed {offset} records...")
```

### Foreign Key Conflicts

**Symptom:** `violates foreign key constraint`

**Solutions:**

1. **Check for orphaned records before migration:**
```sql
-- Find orphaned cart_items
SELECT ci.id, ci.cart_id
FROM cart_items ci
LEFT JOIN grocery_carts gc ON ci.cart_id = gc.id
WHERE gc.id IS NULL;

-- Clean up orphaned records
DELETE FROM cart_items
WHERE cart_id NOT IN (SELECT id FROM grocery_carts);
```

2. **Use CASCADE in migration:**
```python
def upgrade():
    """Add foreign key with CASCADE."""
    op.create_foreign_key(
        'fk_cart_items_cart_id',
        'cart_items', 'grocery_carts',
        ['cart_id'], ['id'],
        ondelete='CASCADE'
    )
```

### Migration Already Applied

**Symptom:** `Target database is not up to date` or `Revision ... already exists`

**Solution:**
```bash
# Check alembic_version table
psql $DATABASE_URL -c "SELECT * FROM alembic_version;"

# Manual fix: stamp to correct version
alembic stamp head

# Or stamp to specific version
alembic stamp 005_add_dietary_tags
```

### Conflicting Migrations

**Symptom:** Multiple head revisions exist

**Solution:**
```bash
# Create merge migration
alembic merge -m "merge conflicting heads" heads

# Edit the generated merge migration
# Then upgrade
alembic upgrade head
```

## Performance Considerations

### Index Creation Timing

**Bad:** Create index during migration (blocks writes)
```python
def upgrade():
    op.create_index('ix_recipes_title', 'recipes', ['title'])  # BLOCKS!
```

**Good:** Create index concurrently (no blocking)
```python
def upgrade():
    connection = op.get_bind()
    connection.execution_options(isolation_level="AUTOCOMMIT")
    connection.execute(sa.text(
        'CREATE INDEX CONCURRENTLY ix_recipes_title ON recipes (title)'
    ))
```

### Batch Operations for Large Tables

For tables with >100K rows, use batching:

```python
def upgrade():
    """Update large table in batches."""
    connection = op.get_bind()

    batch_size = 5000
    total_updated = 0

    while True:
        result = connection.execute(sa.text("""
            UPDATE recipes
            SET normalized_title = LOWER(TRIM(title))
            WHERE id IN (
                SELECT id FROM recipes
                WHERE normalized_title IS NULL
                LIMIT :batch_size
            )
        """), {'batch_size': batch_size})

        updated = result.rowcount
        total_updated += updated

        if updated == 0:
            break

        print(f"Updated {total_updated} records...")

        # Small delay to avoid overwhelming database
        import time
        time.sleep(0.5)
```

### Locking Implications

Different operations have different locking behavior:

| Operation | Lock Type | Blocks Reads? | Blocks Writes? |
|-----------|-----------|---------------|----------------|
| ADD COLUMN | ACCESS EXCLUSIVE | Yes | Yes |
| ADD COLUMN (DEFAULT) | ACCESS EXCLUSIVE | Yes | Yes |
| DROP COLUMN | ACCESS EXCLUSIVE | Yes | Yes |
| ADD INDEX | SHARE | No | Yes |
| ADD INDEX CONCURRENTLY | SHARE UPDATE EXCLUSIVE | No | No |
| ADD CONSTRAINT | ACCESS EXCLUSIVE | Yes | Yes |
| DROP CONSTRAINT | ACCESS EXCLUSIVE | Yes | Yes |

### Maintenance Windows

For large migrations, schedule maintenance windows:

1. **Notify users in advance** (24-48 hours)
2. **Choose low-traffic period** (typically 2-4 AM local time)
3. **Allocate 2-3x estimated time**
4. **Have rollback plan ready**
5. **Monitor application after migration**

## Emergency Procedures

### Database Connection Lost During Migration

```bash
# Check if migration partially applied
alembic current

# Check database state
psql $DATABASE_URL -c "\dt"

# Check alembic_version table
psql $DATABASE_URL -c "SELECT * FROM alembic_version;"

# If partially applied:
# 1. Manually complete remaining steps
# 2. Update alembic_version table
psql $DATABASE_URL -c "UPDATE alembic_version SET version_num = '006_new_revision';"
```

### Critical Bug Found After Migration

```bash
# 1. Enable maintenance mode immediately
# 2. Rollback migration
alembic downgrade -1

# 3. Verify application works
curl https://api.yourapp.com/health

# 4. Fix migration script
# 5. Re-test in staging
# 6. Re-deploy with fixed version
```

### Data Loss During Migration

```bash
# 1. STOP - Don't apply more changes
# 2. Restore from backup
./infrastructure/scripts/restore_database.sh pre_migration_TIMESTAMP

# 3. Verify data restored
psql $DATABASE_URL -c "SELECT COUNT(*) FROM recipes;"

# 4. Investigate what went wrong
# 5. Fix migration script
# 6. Re-test thoroughly before retrying
```

### Common Mistakes to Avoid

1. **Don't modify existing migrations** - Create a new one instead
2. **Don't skip testing locally** - Always test before deploying
3. **Don't forget downgrade()** - Always implement rollback
4. **Don't deploy without backup** - Always backup production first
5. **Don't use autogenerate blindly** - Review generated code carefully
6. **Don't create indexes without CONCURRENTLY** - Use concurrent creation for large tables
7. **Don't forget to import models in env.py** - Autogenerate won't detect changes otherwise
